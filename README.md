# Dashboard

Control plane для парсеров: Django с админкой на [Unfold](https://unfoldadmin.com/),
который знает **что и когда запускать**, раздаёт задания раннерам и ведёт журнал
запусков с логами.

Сами парсеры живут в отдельном репозитории и сами решают, куда складывать данные.
Через control plane данные не проходят — только задания и отчёты о выполнении.

## Стек

| | |
|---|---|
| Django | 5.2 |
| django-unfold | 0.91 |
| БД | SQLite (файл `db.sqlite3`) |
| Расписания | cron-выражения, разбирает croniter |
| Фоновые процессы | нет — расписание считается в момент опроса раннером |
| Пакеты и venv | [uv](https://docs.astral.sh/uv/) — `pyproject.toml` + `uv.lock` |

Системных зависимостей нет. Нужен только `uv` — нужный Python он поставит сам.

## Запуск

```bash
make install     # uv sync: создаст .venv и поставит зависимости по локу
make migrate
make superuser
make run
```

Админка: http://127.0.0.1:8000/admin/

Без Makefile — то же самое напрямую:

```bash
uv sync
uv run manage.py migrate
uv run manage.py createsuperuser
uv run manage.py runserver
```

`uv run` сам поднимает окружение — активировать venv не нужно.
Если uv ещё не стоит:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh                  # macOS / Linux
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"        # Windows
```

## Docker

Вариант без установки Python и uv на машину.

```bash
docker compose up -d --build     # или make docker-up
docker compose run --rm web python manage.py createsuperuser
```

Админка: http://127.0.0.1:8000/admin/ — порт меняется переменной `PORT`.

`migrate` прогоняет миграции и завершается, затем стартует `web`. Миграции
вынесены в отдельный шаг намеренно: у SQLite один писатель, и параллельный
`migrate` из двух контейнеров может встать на блокировке.

Раннер вынесен в профиль — в бою он живёт в репозитории парсеров, но для
локальной проверки поднимается вместе с остальным:

```bash
RUNNER_TOKEN=... docker compose --profile runner up -d
```

```bash
make docker-logs         # логи всех сервисов
make docker-down         # остановить; том с базой остаётся
docker compose down -v   # остановить и удалить базу
```

Код прокинут внутрь контейнера томом, поэтому правки видны без пересборки —
образ нужно пересобирать только при изменении зависимостей (`uv.lock`).
Виртуальное окружение лежит в `/venv`, вне `/app`, чтобы bind-mount его не перекрывал.
База — в именованном томе по пути `/data/db.sqlite3` (переменная `DJANGO_DB_PATH`).

## Команды

`make help` покажет список. Основное:

| Команда | Что делает |
|---|---|
| `make install` / `make sync` | зависимости: по локу / строго по локу, без перерешения |
| `make lock` / `make upgrade` | пересобрать лок / поднять версии в пределах ограничений |
| `make run` | сервер разработки, порт меняется через `PORT=8080` |
| `make runner` | референсный раннер (нужен `RUNNER_TOKEN`) |
| `make maintenance` | просроченные запуски и чистка старых логов |
| `make migrate` / `make migrations` | применить / создать миграции |
| `make test` | тесты |
| `make lint` / `make fmt` | проверить / отформатировать код (ruff) |
| `make check` | `manage.py check` + проверка несозданных миграций |
| `make ci` | всё, что гоняет CI: lint + check + test |
| `make clean` / `make distclean` | убрать кэши / ещё и venv с базой |
| `make docker-up` / `make docker-down` | поднять / остановить всё в Docker |
| `make docker-build` / `make docker-logs` | пересобрать образ / смотреть логи |
| `make docker-superuser` / `make docker-shell` | суперпользователь / shell в контейнере |

## Структура

```

config/urls.py       / → редирект на /admin/

```

## Как это настроено

**Unfold идёт первым в `INSTALLED_APPS`** — до `django.contrib.admin`, иначе его шаблоны не подхватятся.

**Своя админ-модель наследует ModelAdmin из Unfold:**

```python
from unfold.admin import ModelAdmin

@admin.register(Article)
class ArticleAdmin(ModelAdmin):
    list_display = ("title", "created_at")
```

Для моделей, у которых уже есть готовый ModelAdmin (User, Group), миксуются оба —
см. `core/admin.py`.

**Сайдбар** задаётся вручную в `UNFOLD["SIDEBAR"]["navigation"]` — новые разделы
нужно дописывать туда, автоматически они не появляются.

## Как это работает

```
Django (control plane)                 Раннер (отдельный репозиторий)
  источники, расписание, журнал   ←──   опрашивает: «есть работа?»
  выдаёт задание                  ──→   выполняет парсер
  принимает логи и отчёт          ←──   шлёт логи пачками и результат
```

Фоновых процессов нет. Когда раннер приходит за заданием, Django в этот момент:
возвращает в очередь просроченные запуски, создаёт запуски для источников,
которым пора по cron, и атомарно отдаёт одно задание.

**Источник** — что запускать: ключ парсера, параметры (JSON), cron, уровень логов.
Ключ и параметры интерпретирует раннер, control plane в них не заглядывает.

**Запуск** — журнал: статус, тайминги, счётчики, ошибка и непрозрачная ссылка
на то, куда раннер положил данные.

**Данные в control plane не хранятся.** Схема данных живёт в парсере и может
меняться без миграций здесь.

### Управление из админки

| Раздел | Что делает |
|---|---|
| Источники | создать, поменять cron и параметры, включить и выключить, кнопка «Запустить сейчас» |
| Запуски | история со статусами и счётчиками; на странице запуска — лента лога, пока запуск идёт, она сама обновляется |
| Логи | сквозной просмотр по всем источникам: например, все ошибки за сутки |
| Раннеры | токены и время последней активности |

Источник отключается автоматически после N неудач подряд (поле «отключить после
N неудач», 0 — не отключать).

### API для раннеров

Аутентификация — токен раннера в заголовке `X-Runner-Token`.

| Метод | Назначение |
|---|---|
| `POST /api/v1/runs/claim/` | забрать задание; пустой ответ — работы нет |
| `POST /api/v1/runs/<id>/logs/` | отправить пачку строк лога, продлевает аренду |
| `POST /api/v1/runs/<id>/heartbeat/` | «жив, работаю» — продлить аренду |
| `POST /api/v1/runs/<id>/complete/` | завершить: статус, счётчики, ссылка на результат, ошибка |

Если раннер пропал, запуск висит не вечно: у задания есть срок аренды, по его
истечении запуск помечается просроченным и источник получает неудачу.

### Логи

Парсер пишет обычным `logging` — раннер подсовывает обработчик, который копит
строки и отправляет их пачками. В логи не должны попадать сами данные: только
счётчики, идентификаторы и URL, иначе данные просочатся в control plane
через чёрный ход.

Ограничители на стороне Django: не больше 10 000 строк на запуск, длина строки
до 4 000 символов, срок хранения 30 дней. Настраивается словарём `CONTROL`
в `config/settings.py`.

### Раннер

В `runner/` лежит референсная реализация на одной стандартной библиотеке —
её место в репозитории парсеров, здесь она для прогона всего цикла.

```bash
uv run manage.py runserver            # control plane
# создайте раннер в админке и скопируйте токен
DASHBOARD_URL=http://127.0.0.1:8000 RUNNER_TOKEN=... python runner/runner.py
```

Флаг `--once` — выполнить одно задание и выйти, удобно для отладки; если
control plane недоступен, раннер с этим флагом завершается с кодом 1.

### Обслуживание

```bash
uv run manage.py maintenance          # просроченные запуски + чистка логов
```

Вешается на системный планировщик (cron, systemd timer, Планировщик заданий).
Ключи `--log-days`, `--run-days`, `--dry-run`.

## CI

GitHub Actions (`.github/workflows/ci.yml`) на каждый push в `main` и на каждый PR:

| Job | Что делает |
|---|---|
| Линтер | `uv sync --locked`, затем `ruff check` + `ruff format --check` |
| Тесты | `manage.py check`, проверка несозданных миграций, `manage.py test`, `collectstatic` на Python 3.11 / 3.12 / 3.13 |

Оба job'а ставят зависимости через `uv sync --locked`: версии берутся из `uv.lock`,
CI падает, если лок разошёлся с `pyproject.toml`. После правки зависимостей нужно
закоммитить обновлённый `uv.lock` (`make lock`).

Локально то же самое — `make ci`.

## Настройки окружения

Настройки читаются из переменных окружения. Локально удобнее держать их в `.env`:

```bash
cp .env.example .env
```

Файл в git не попадает (`.env.example` — попадает, это шаблон). Читает его
`load_env_file()` в `config/settings.py` — без внешних зависимостей. Правила:
переменная, уже заданная в окружении, побеждает файл; при дубле ключа в файле
побеждает последняя строка; строки с `#` и пустые игнорируются, кавычки снимаются.

`docker compose` подхватывает тот же `.env` сам — и для подстановки `${...}`
в `compose.yaml`, и как `env_file` внутри контейнеров (если файла нет, всё работает
на значениях по умолчанию).

| Переменная | По умолчанию |
|---|---|
| `DJANGO_SECRET_KEY` | небезопасный ключ для разработки |
| `DJANGO_DEBUG` | `1` |
| `DJANGO_ALLOWED_HOSTS` | `*` |
| `CONTROL_LEASE_SECONDS` | `600` — срок аренды задания |
| `CONTROL_LOG_RETENTION_DAYS` | `30` — сколько хранить строки логов |
| `CONTROL_POLL_INTERVAL` | `10` — рекомендуемый интервал опроса, отдаётся раннеру |
| `RUNNER_TOKEN`, `DASHBOARD_URL` | читает раннер: токен из админки и адрес control plane |
| `DJANGO_DB_PATH` | `db.sqlite3` в корне проекта; в Docker — `/data/db.sqlite3` |
| `PORT` | `8000` — порт, на котором админка доступна на хосте (Docker и `make run`) |

Перед деплоем обязательно задать свой `DJANGO_SECRET_KEY`, выключить `DJANGO_DEBUG`
и перечислить реальные хосты в `DJANGO_ALLOWED_HOSTS`.

## Зависимости

Добавить пакет: `uv add <пакет>` (в dev-группу: `uv add --dev <пакет>`) — uv сам
обновит `pyproject.toml`, `uv.lock` и окружение. Удалить: `uv remove <пакет>`.
`uv.lock` коммитится, `.venv/` — нет.

## Что дальше

- Перенести `runner/` в репозиторий парсеров и убрать отсюда — здесь он
  временно, для прогона цикла.
- Цепочки шагов: запускать обработку после успешного парсинга того же источника.
- Проверки качества по истории счётчиков: «ноль записей два раза подряд» или
  «записей вдвое меньше среднего» — пометить подозрительным.
- Свой дашборд на главной, когда будет что показывать: создать каталог
  `templates/`, вернуть его в `TEMPLATES["DIRS"]`, положить туда
  `admin/index.html` и указать `UNFOLD["DASHBOARD_CALLBACK"]`.
- Русская локаль для Unfold: часть строк интерфейса («Type to search», «Filters»)
  остаётся английской, лечится собственным `.po`-файлом.
- Гео-слой (SpatiaLite + GDAL + карты в формах) — рабочий вариант лежит в истории,
  коммит `d5efad7`: `git show d5efad7 --stat`.
