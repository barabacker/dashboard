# Бэк-офис сбора данных

*English version: [`README.md`](README.md)*

Человек описывает, **что** собирать (`Config`) и, при необходимости, **когда** (`Schedule`).
Система фиксирует, **что действительно выполнялось** (`Job`). Алгоритмы сборщиков — это код,
а не данные.

Модульный монолит на Django, одна база PostgreSQL, один деплой. Ни брокера, ни Celery, ни Redis —
очередью *служит* сама таблица `Job`.

* Обоснование решений в control (модели, формы, админка): [`docs/superpowers/specs/2026-07-31-control-models-redesign-design.md`](docs/superpowers/specs/2026-07-31-control-models-redesign-design.md)
* Исходная спецификация: [`docs/spec/claude-code-build-prompt.md`](docs/spec/claude-code-build-prompt.md)

## Структура

```
Makefile             pyproject.toml       uv.lock
src/                 manage.py и четыре пакета
tests/               unit/ — чистые тесты; остальные работают с БД
docker/              Dockerfile + compose.yaml
docs/                оснастка агента · архитектурные ADR · спецификация · бандл Architect
```

| Пакет | Отвечает за | Правило |
|---|---|---|
| `src/collectors/` | алгоритмы сборщиков, схемы их параметров и перенесённый движок парсинга | чистый лист — не импортирует ничего из проекта, даже Django |
| `src/control/` | **все** модели, админку, дашборд, единственную функцию `enqueue` | никогда не импортирует рантайм исполнения и код раннеров |
| `src/execution/` | claim/lease/reclaim, цикл воркера, планировщик | **никаких** моделей; свободно импортирует `control` и `collectors` |
| `src/project/` | settings, urls, wsgi | обвязка фреймворка |

Это проверяется `import-linter`, а не дисциплиной ревью:

```bash
make contracts
```

## Запуск

Для всего рутинного есть цель в `make`. `make` без аргументов печатает список.

### Docker

```bash
make env && make up
```

`make env` создаёт `.env` из примера — там задаётся `COMPOSE_FILE`, благодаря которому обычный
`docker compose` находит `docker/compose.yaml` из корня репозитория. `make up` поднимает Postgres,
веб-приложение на http://localhost:8000, воркер и планировщик. Дальше:

```bash
make docker-migrate && make docker-seed
```

`seed` создаёт суперпользователя `admin` / `admin`, синхронизирует проекцию сборщиков и добавляет
три примера `Config` — среди них один намеренно невалидный для текущей версии сборщика, чтобы
поведение fail-fast было видно с первой минуты.

### Локально

Нужен [uv](https://docs.astral.sh/uv/). Postgres при этом можно по-прежнему брать из compose.

```bash
make install && make env && make db
```

`make install` выполняет `uv sync`, который ставит проект в editable-режиме — именно это добавляет
`src/` в путь импорта.

```bash
make migrate && make seed && make run
```

Затем воркер в одном терминале и планировщик в другом:

```bash
make worker
```

```bash
make scheduler
```

`make tick` — один проход планирования; штатный способ развёртывания — системный cron раз в минуту.
`make scheduler` (`--loop`) существует для compose и для хостов без cron.

## Интерфейсы

Интерфейс — на **русском**; код, логи, хранимые значения и документация остаются английскими.

* **`/admin/`** — основной интерфейс. `Config` с расписаниями inline, история `Job` и страница
  сборщика, показывающая схему параметров прямо из кода.
* **`/admin/control/source/`** — «Источники»: сайты торговых площадок, которые обходят парсеры.
  Это те же `Config`, но спрашиваются как сайт — домен, путь к листингу, костыли под TLS —
  а не как JSON-объект.
* **`/dashboard/`** — небольшая HTMX-страница: что каждый `Config` делал в последний раз, что
  выполняется сейчас, «Запустить сейчас» и «Отменить». Действия — обычные POST-формы; HTMX только
  автообновляет панель заданий.

Время отображается в `DJANGO_TIME_ZONE` (по умолчанию `UTC`; укажите `Europe/Moscow` в `.env`,
чтобы читать местное время). Хранится всегда UTC.

## Сбор с торговых площадок

В коде есть четыре сборщика для площадок банкротных торгов — по одному на семейство парсеров:
`tender_fogsoft`, `tender_kendo`, `tender_btorg`, `tender_ruson`. Сам движок перенесён в
`src/collectors/engine/` и по-прежнему не зависит ни от какого фреймворка.

**Сборщик — это движок, а источник — это данные.** Домен, путь к листингу и костыли под TLS —
обычные параметры, поэтому добавить источник значит заполнить форму: списка сайтов в репозитории
нет. `make sources` переносит 33 источника, которые уже обходил временный проект; дальше они
живут в админке.

Запуск честно ходит по сайту, между запросами проверяет отмену и продлевает аренду. Задача
сообщает, что нашла — `rows`, `calls`, `listing_pages` и несколько `lot_id` в `Job.result`, — и
сохраняет сами лоты через `Lot` / `DbLotSink`; в `Job.result` лежит `"stored": true` (или `false`
для редкого запуска без приёмника), чтобы зелёная задача не создавала ложного впечатления.

## Команды

`make help` перечисляет все цели. Специфичные для этой системы:

| Цель | Команда под ней | Что делает |
|---|---|---|
| `make collectors` | `sync_collectors` | Отражает реестр сборщиков в таблице-проекции. Запускать при деплое. Доступен `--dry-run`. |
| `make seed` | `seed` | Данные для разработки. Идемпотентно. |
| `make sources` | `seed_sources` | Создаёт 33 торговые площадки, перенесённые из временного проекта парсеров. Это стартовые данные, а не источник правды: дальше источники правятся в админке. Идемпотентно, есть `--dry-run`. |
| `make worker` | `run_worker` | Забирает и выполняет `Job`. `--once`, `--max-jobs`, `--lease-seconds`, `--poll-seconds`. Запускайте сколько угодно — они конкурируют за строки. |
| `make tick` / `make scheduler` | `run_scheduler` | Один проход планирования либо `--loop`. Также `--interval`, `--max-catchup`. |

Чтобы передать флаги, вызывайте management-команду напрямую — `manage.py` лежит в `src/`:

```bash
uv run python src/manage.py run_worker --once
```

## Как это держится вместе

**Постановка в очередь — одна функция**, общая для «Запустить сейчас» и планировщика. Она
проверяет, что `Config` включён и не архивирован, разрешает *текущую* версию сборщика, валидирует
заданные параметры по схеме этой версии и пишет `Job` с полным снимком: `collector_key`,
`collector_version`, `effective_parameters`, `schema_version`, `config_id`, `config_revision`.
Запуск воспроизводится по одному этому снимку — исполнение больше никогда не читает `Config`,
поэтому правка или архивация на лету ничего не меняет для уже идущего запуска.

**Секреты никогда не попадают в снимок.** Параметры несут *ссылку* на учётные данные (имя
переменной окружения); значение разрешается во время исполнения. Поэтому «воспроизводимость»
означает *та же цель, те же параметры, тот же код версии* — ротация секретов и есть
задокументированное исключение.

**Очередь — один SQL-оператор.** `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED
LIMIT 1)` с дизъюнктом по истёкшей аренде, который заодно возвращает задания умерших воркеров.
Отдельного процесса-сборщика мусора нет, потому что он не нужен.

**Возврат по аренде — не повтор.** `attempt_no` считает передачи между исполнителями. `Job`,
дошедший до терминального `failed`, никогда не ставится в очередь заново автоматически — повтор
это новый `Job`. По истории можно отличить «воркер умирал трижды» от «сборщик упал один раз».

**Идемпотентность планирования держится на ограничении, а не на блокировке.** Создание `Job` и
сдвиг `last_fired_at` происходят в одной транзакции под защитой уникального ограничения на
`(schedule_id, fire_time)`. Наложившиеся запуски cron, два планировщика, падение на середине —
ничто из этого не поставит задание дважды.

**Версии сборщиков вечны.** Каждая пара `(key, version)` — свой модуль-раннер, который никогда не
правится на месте; снимок годичной давности по-прежнему разрешается в тот код, который тогда и
выполнялся.

## Проверки

```bash
make verify
```

Системная проверка Django, расхождение миграций, ruff, контракты импортов и набор тестов — тот же
барьер, который прогнал бы CI.
